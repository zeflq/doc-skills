---
name: doc-routing
description: "Use when placing, updating, or syncing agent-readable .md files in a project. Handles CREATE (new doc from topic), UPDATE (edit a section), and SYNC (update notes from a git range, after a sprint, after a PR, or after X commits). Triggers on phrases like: sync notes, update the notes, sync my docs, create a note, add a doc, update the doc, new note. Loads placement rules, plans doc syncs, then delegates writing to doc-writing."
---

# doc-routing Skill

<context-routing>
| User intent | Workflow |
|---|---|
| "add", "create", "new doc", "new note", "new file" | CREATE workflow |
| "update", "edit", "fix", "improve", "clarify" | UPDATE workflow |
| "sync", "docs after code", "git changes", "commit range" | SYNC entry |
</context-routing>

<config>
  root: .pi/notes/
  subdirs: []
  pattern: "{subdir}.{topic}.md"
  skip_patterns: ["**/*.lock", "**/dist/**", "**/*.generated.*", "**/build/**", ".pi/skills/**"]
  never_skip: []
</config>

<core-rules>
  <rule><requirement>Never proceed until placement rules are confirmed.</requirement><example>Stop before writing if the root path or naming pattern is still unknown.</example></rule>
  <rule><requirement>Every file must have YAML frontmatter with `description:` starting with "Load when" or "Use when".</requirement><example>`description: Load when working in the payments service.`</example></rule>
  <rule><requirement>Keep one topic per file.</requirement><example>Split auth and billing into separate files instead of merging them.</example></rule>
  <rule><requirement>Never classify `_index.md` as a sync or grouping topic — it is always generated by `<write-index>` and never represents a code domain.</requirement><example>`_index.md` appears in git diff or `git ls-files` → skip it in all classification and grouping steps.</example></rule>
</core-rules>

<delegation>
  <rule>
    <requirement>Read `skills/doc-writing/SKILL.md` with `read` before any write step.</requirement>
    IF loaded → execute its full workflow inline (including pre-flight) — do not treat it as a separate agent or simulate its output.
    ELSE → stop and output: "doc-writing skill not found — install it before running doc-routing." Do not offer alternatives or options.
    <example>doc-writing loaded → follow its CREATE/UPDATE steps directly using provided file contents as input.</example>
  </rule>
  <rule><requirement>When executing doc-writing inline, resolve all doc-writing `references/` paths to `skills/doc-writing/references/` (e.g. `references/techniques.md` → `skills/doc-writing/references/techniques.md`).</requirement><example>doc-writing pre-flight reads `references/techniques.md` → read `skills/doc-writing/references/techniques.md` instead.</example></rule>
  <rule><requirement>Apply project placement rules to every linked file doc-writing creates.</requirement><example>A split-off linked file must still follow `{subdir}.{topic}.md`.</example></rule>
</delegation>

<sync-entry>
  When SYNC intent detected, route before running any git command:
  IF any range bound is a branch name (not a commit hash and not a vX.Y tag) → output exactly: "Ranges must use commit hashes or version tags (e.g. v1.2). Provide a hash or tag instead." and terminate. Do not run any git commands.
  ELSE IF explicit range provided → read `references/sync.md` with `read` tool, run SYNC workflow.
  ELSE IF `{root}/.last-sync` exists → read `references/sync.md` with `read` tool, run SYNC workflow.
  ELSE →
    List `{root}` to check for existing docs (treat missing directory as empty).
    IF no docs exist → read `references/cold-start.md` with `read` tool now — cold-start scans all files automatically, no starting point needed from user — run COLD-START workflow from step 1.
    ELSE → output exactly: "No last-sync found. Provide a starting commit or range." and terminate.
  <example>"sync from last 3 commits" → explicit range → SYNC · "sync notes" + .last-sync exists → SYNC · "sync notes" + no .last-sync + empty {root} → COLD-START · "sync notes" + no .last-sync + docs exist → hard stop.</example>
</sync-entry>

<workflows>
  <create>
    <step number="1">
      Derive subdir from user intent by matching topic against config subdirs.
      IF subdirs is non-empty AND topic matches a config subdir → place under `{root}/{subdir}/{subdir}.{topic}.md`.
      ELSE → derive a domain prefix from the topic and place flat in `{root}/{prefix}.{topic}.md`. Note: `subdirs: []` means flat layout — prefix is a short domain category (e.g. `back`, `front`, `github`) — never use the topic name itself as the prefix.
      <example>subdirs: [] + topic `ui` → prefix `front` → `.pi/notes/front.ui.md` (not `ui.ui.md`) · subdirs: ["back"] + topic `proxy errors` → `.pi/notes/back/back.proxy-errors.md`</example>
    </step>
    <step number="2"><action>Execute doc-writing full workflow inline (including pre-flight) with the resolved path and project constraints.</action><example>Follow doc-writing steps directly — do not simulate or substitute.</example></step>
    <step number="3"><action>Run the validation checklist.</action><example>Check frontmatter, topic scope, and path naming before finish.</example></step>
    <step number="4">Execute `<write-index>`.</step>
  </create>

  <update>
    <step number="1"><action>Load the existing file using config path rules.</action><example>Read `.pi/notes/back.auth.md` before changing any section.</example></step>
    <step number="2"><action>Show a one-line summary per section.</action><example>Summaries: error-mapping, handling-rules, logging — user picks handling-rules.</example></step>
    <step number="3">
      IF requested section exists → proceed with doc-writing UPDATE on that section only.
      ELSE → ask: "No [section] found. Add it as a new section, or update an existing one? ([closest section] covers related content.)"
      <example>Retry section missing → ask before adding: "No retry section found. Add as new section, or update handling-rules (closest match)?"</example>
    </step>
    <step number="4"><action>Execute doc-writing full workflow inline (including pre-flight) on the confirmed section only. Skip doc-writing UPDATE step 3 — section already resolved.</action><example>Edit handling-rules without touching error-mapping or logging. Doc-writing does not re-prompt for section selection.</example></step>
    <step number="5"><action>Run the validation checklist.</action><example>Verify only the targeted section changed.</example></step>
    <step number="6">Execute `<write-index>`.</step>
  </update>
</workflows>

<write-index>
  <rule>Execute the write — do not narrate it. Not complete until `{root}/_index.md` is physically written.</rule>
  List all .md files under `{root}` (excluding `_index.md` and `.last-sync`). Write `{root}/_index.md` as a markdown list of links. No metadata, no dates.
  <example>`- [back.auth.md](back.auth.md)` — not `- back.auth.md — updated 2026-05-16`.</example>
</write-index>

<validation-checklist>
  <check>Every file has frontmatter with a `description:` that starts with "Load when" or "Use when".</check>
  <check>Each file covers exactly one topic.<example>Auth and billing never share one doc.</example></check>
  <check>doc-writing was executed inline — not simulated, not delegated away.</check>
</validation-checklist>
